# 团轴 vNext：独立计划、WCL 导入、插件导出与大陆部署

## 基本信息

- 优先级：P0
- 状态：开发中（vNext v1 对象模型与现有工作流切换已完成）
- 提出时间：2026-08-11
- 目标版本：Raidline vNext（计划 schema v1、目录 schema v1、战斗快照 schema v1、转换规则 schema v1）
- 主要用户：当前史诗团本开荒团长与协助排轴的管理者
- 文档用途：作为后续讨论基线，并可在确认后直接交给 AI 按里程碑实施

> 除非后续讨论明确修改，本文“固定决策”与验收标准均视为默认实施要求。实现者不得自行扩大范围，也不得为了兼容旧实现而改变本文的数据语义。

## 一、产品定义

Raidline 是一个面向团长的战术编排、战斗记录导入、插件导出与有限对比分析工具，不是完整攻略站、通用日志分析平台或成员门户。

产品应完成以下闭环：

1. 必须可以从当前 Boss 预设或空白计划独立建轴，不需要 WCL。
2. 填入当前名单与策略分组，安排玩家技能和非技能战术任务。
3. 调整预计阶段时间并检查跨阶段技能可用性。
4. 临时换人或复制下一轮安排。
5. 必须可以导出可直接在 MRT 或其他 Reminder 插件中使用的文本。
6. 可选地粘贴公开 WCL 战斗链接，导入人员、Boss 技能轴和玩家关键技能，方便参考其他团队的实际执行。
7. 可选地在开荒后导入新的 WCL 战斗，对比计划与实际执行；对比默认只读，不自动修改计划。
8. 游戏目录更新后，已有 vNext 计划仍按原快照打开，并由用户主动决定是否升级。

完成后的核心价值应是：团长不再重复手写 MRT，不必在换人、转阶段或目录更新后重做整条轴；可以借助 WCL 减少抄轴和复盘的机械工作，但 WCL 不可用时，建轴、编辑、保存、分享和导出必须全部正常。

## 二、固定产品决策

### 2.1 必须能力与可选能力

- 必须能力：从预设或空白计划创建、完整编辑、本地保存、检查点、显式发布、只读分享、MRT 与其他 Reminder 导出。
- 可选能力：公开 WCL 链接导入、从 WCL 创建计划草稿、将 WCL 与现有计划对比。
- WCL 是核心集成能力，但不是计划运行依赖。任何 WCL 认证、网络、额度或数据错误都不得阻断必须能力。
- 计划、目录和导出器使用 Raidline 自有的稳定模型；WCL 仅通过适配器映射到该模型。
- WCL 导入得到的是一次性快照和候选转换结果，不是持续同步关系。

### 2.2 保存、发布与生产部署

- 保持本地优先：工作副本、撤销历史和检查点继续保存在 IndexedDB。
- 保持显式发布：只有用户主动发布时才将计划快照写入服务端对象存储。
- 不增加普通用户账号、云端自动保存或实时多人协作。
- 普通用户只看到当前最新版目录；旧目录 release 仅供内部差异比较，不提供旧版本选择界面。
- 每份计划内嵌应用时的技能、阶段和机制快照，不能在打开时实时引用最新目录 JSON。
- 最终生产环境部署在中国大陆普通 Linux 服务器；应用服务、数据库和长期数据目录位于同一服务器或同一私有网络，不让浏览器直接连接数据库。
- 当前阶段只做本地开发和测试，不维护任何第三方托管平台部署适配器；前端回归使用本地 Vinext 运行时和匿名 fixture。
- 生产代码不得依赖托管平台专有 API 或运行时绑定；服务端持久化必须收敛到可替换的 `ObjectStore`/数据库接口。
- 在当前单站点、低写入并发前提下，生产默认使用服务器本地 SQLite（WAL 模式）保存结构化索引、任务状态和版本元数据；正文与大型不可变 JSON 使用服务器持久数据目录中的内容寻址文件。
- 只有出现多实例部署、明显写入竞争、高可用或运维团队明确要求时，才将 SQL 适配器升级为 PostgreSQL；不得为了“以后可能需要”同时维护两套生产数据库。
- 生产始终只有一套权威数据库和一套权威对象目录，禁止 SQLite/PostgreSQL 或不同对象目录之间长期双写。新基础设施只有在降低已观察到的风险或满足已确认容量需求时才能引入。
- 数据库、对象目录和配置均需纳入备份与恢复演练。任何文件必须先完整写入并校验哈希，再提交数据库引用，避免数据库指向半写入文件。
- 本地验证只使用被 Git 忽略的数据目录或固定测试数据，不得因此产生第二套业务语义。

### 2.3 WCL 集成边界

- 首版支持粘贴 WCL v2 公共 API 可读取的公开战斗链接；私有报告 OAuth、账号绑定和长期授权不在本轮范围。
- WCL client secret 只存在于服务端配置，浏览器不得获取 access token、client secret 或直接调用需要密钥的接口。
- WCL 链接解析必须接受 `cn.warcraftlogs.com` 等官方区域域名；后端 API base URL 可配置，并在大陆生产部署时通过真实认证请求比较官方大陆可用入口与 WCL 文档所列入口后确定，禁止在代码中硬编码“必然跨境”或“必然同境”的假设。
- WCL 读取采用异步任务、分页、超时、有限重试、退避和幂等缓存；服务器到 WCL 的外部网络失败必须表现为可重试的导入失败，而不是页面或计划损坏。
- 首版只接受史诗难度战斗。难度只在 WCL 请求边界临时判断；非史诗战斗返回 `UNSUPPORTED_DIFFICULTY`，且不得创建战斗快照、导入草稿或计划。
- 同一来源以 `reportCode + fightId + reportRevision` 标识 WCL 版本，同时保存规范化内容哈希；相同版本和内容不得重复创建快照。
- WCL 返回事件并非持久化真值。服务端只保存规范化且与排轴相关的快照，不长期镜像完整原始 GraphQL 响应。
- 快照一旦成功保存即不可变。WCL 报告更新时创建新快照，不覆盖已有 vNext 计划、既有导入或既有对比结果。
- 用户明确导入成功的规范化快照默认长期保留且不自动过期；管理员删除前必须看到被哪些导入和对比引用。删除来源不级联删除计划，历史对比改为“来源已删除”。
- 从 WCL 创建的成员、机制和技能安排必须复制完整值到计划；来源引用只用于追溯，删除来源后计划仍可编辑、发布和导出。
- WCL 无法还原团长未执行的备用安排、提醒文本或战术意图；这些内容必须由用户补充，界面不得把推测显示为已确认计划。

### 2.4 时间与阶段

- 底层只有一条完整时间轴；“全程、P1、转阶段、P2”等标签只是同一时间轴的聚焦视图。
- 网站中的“绝对时间”统一改称“开怪计时”。
- 阶段预计开始时间只用于网站布局与冲突检查，不代表实战转阶段的硬编码时间。
- 导出到支持阶段的插件时使用阶段内时间，不使用网站预计的全局时间替代。
- 动态阶段不做击杀模拟；冲突检查以条件形式告诉团长阶段最早可进入时间。

### 2.5 技能、任务与说明

- 技能安排与战术任务是两种不同对象。
- 技能安排负责职业兼容、CD、充能、GCD、施法与持续时间检查。
- 战术任务负责“谁在什么时候做什么”，不要求绑定技能。
- 阶段说明负责没有精确提醒时间的文字，不制造虚假技能或虚假执行人。
- 首版不区分“执行者”和“提醒受众”；提醒默认只面向任务执行者。阅读版笔记仍可由全团查看。

### 2.6 名单与分组

- 策略组是可选的多对多关系，一个成员可以属于多个策略组。
- 策略组不等同于游戏内 1～4 小队。
- 计划内部保存策略组语义；只有导出器需要时才展开为具体玩家名。
- 一键替换成员应复用原 roster slot 的稳定 ID，而不是删除旧成员并创建新 ID。
- WCL 战斗快照保留原玩家姓名、服务器、职业和专精；复制进计划的成员槽位只保存角色名称、职业、专精、职责等排轴信息，不保存服务器或 WCL actor ID。替换成自己团队成员时复用槽位 ID，并保留该槽位的技能安排、战术任务和策略组。
- WCL report actor ID 只在对应报告快照内有效，不能作为计划成员 ID 或跨报告角色身份。

### 2.7 人工事件选择与转换

- 哪个 encounter 需要读取哪些敌方 WCL 事件、哪些事件能转换为阶段或 Boss 机制，必须由人工维护的版本化 `EncounterConversionProfile` 决定。
- 个人减伤、治疗等玩家技能使用独立、版本化的全局 `PlayerSkillExtractionProfile`；它引用全局技能定义，在 fight 元数据与难度校验后统一应用，不复制到每个 Boss profile。
- 两类 profile 都分开维护“采集规则”和“转换/提取规则”：采集规则限制从 WCL 请求并长期保存的事件范围，后者把已采集事件映射为 Raidline 候选对象。
- 不得默认保存整场战斗的全部伤害、治疗和资源事件，也不得仅凭事件名称自动创建正式目录条目。
- 转换规则先以草稿编辑，通过样例战斗预览和校验后显式发布；已发布版本不可修改，只能创建下一版本。
- 每次用户导入仍需看到人员、阶段、机制、玩家技能、未知事件、重复项和推断关系的预览，并由用户确认写入范围。
- 未匹配事件可以显示为候选，但不会自动污染计划或已发布目录。
- “是否生成时间轴对象”与“是否具有未来复盘价值”是两个独立维度。当前优先实现 WCL 战斗记录到时间轴的转换；配对、标签、结果验证或未来复盘事件可以保留标记，但不得因此自动生成时间轴对象。
- 只有跨样本时间稳定、机制语义明确且要求玩家处理的敌方事件才进入时间轴；小怪死亡、随机机制、玩家失误、失败路径或证据不足的事件保持待审，不猜测转换。

### 2.8 导出

- 计划内部不保存 MRT、STT 或 NSRT 的插件语法。
- 所有插件文本由独立导出器从统一计划模型编译生成。
- 首个目标是 MRT 阅读版和 MRT/Kaze 计时版，其次是 NSRT，最后是 STT。
- 首版不生成 MRT 原生 Reminders 序列化配置。
- 导出无法无损表达某项内容时必须给出警告，禁止静默生成可能错误的时间。

## 三、当前实现基线与已知缺口

当前仓库已经具备：

- 全新的 plan、catalog、combat-log、conversion schema v1；严格运行时解析拒绝旧版本、未知字段、重复 ID 和超限计划。
- `metadata / encounter / sources / definitions / roster / timeline` 分层，以及计划内技能、机制完整快照。
- pull、phase 和 mechanic 三类统一时间锚点；机制锚点支持 `cast-start`、`impact` 与 `end`。
- 阶段、机制实例、战术任务、战术说明和技能安排，以及由 `TimelineScene` 派生的显示范围、轨道和诊断。
- 多策略组、可选 1～8 小队、稳定成员槽位和严格目标选择器。
- 本地自动保存、检查点、多标签页冲突、撤销重做、只读发布、复制回本地和 16+4 分享规则。
- 技能 CD、充能、GCD、施法/引导重叠、变体一致性和职业专精兼容诊断。
- 统一 `ExportRequest → ExportResult` 契约及 MRT 阅读版；无法可靠表达的阶段触发或锚点会产生显式警告或阻断错误。
- 提供者无关的 WCL 战斗快照、人工转换规则、导入草稿和对比结果契约及固定 fixture；尚不发起真实网络请求。
- 可替换 `ObjectStore` 边界与本地文件适配器；本阶段未连接生产数据库。

当前后续缺口：

- 真实 WCL v2 服务端客户端、异步任务、认证、分页、幂等快照持久化和用户确认导入流程。
- encounter 级转换规则管理、发布界面与真实 Boss 样例数据。
- 计划与实际战斗的对比计算和交互。
- MRT/Kaze、NSRT、STT 等后续导出器与游戏内真实导入验收。
- 中国大陆普通 Linux 服务器运行包、SQLite/内容寻址文件存储、备份和恢复演练；当前本地分享由被 Git 忽略的文件 `ObjectStore` 适配器承载。

## 四、目标数据模型

### 4.1 统一时间锚点

新增以下公共类型：

```ts
export type TimelineAnchor =
  | { kind: "pull"; offsetMs: number }
  | { kind: "phase"; phaseId: string; offsetMs: number }
  | {
      kind: "mechanic";
      mechanicOccurrenceId: string;
      point: "cast-start" | "impact" | "end";
      offsetMs: number;
    };
```

规则：

- `pull` 相对开怪时间。
- `phase` 相对指定阶段开始时间。
- `mechanic` 相对指定机制实例的施法开始、命中或结束时刻；命中与结束由定义快照中的施法和持续时间派生。
- 时间锚点是唯一持久化真值，解析后的全局 `atMs` 不写回计划正文。
- 所有显示、排序、拖动、冲突检查和导出统一调用锚点解析器。
- 解析失败的对象不得被删除；应进入“未解析”状态并显示明确警告。

### 4.2 阶段

```ts
export interface RaidPhase {
  id: string;
  name: string;
  ordinal: number;
  estimatedStartMs: number;
}
```

规则：

- `id` 是稳定 occurrence ID，不因阶段改名或预计时间变化而改变。
- `ordinal` 是线性导出序号，必须唯一且从 1 开始。
- 重复阶段也必须使用不同 ID 和 ordinal；显示名称可以重复。
- P1 的 `estimatedStartMs` 固定为 0。
- 后续阶段必须按 ordinal 排序，预计时间不得早于前一阶段。
- 移动阶段边界只改变 `estimatedStartMs`；所有阶段相对对象的 `offsetMs` 保持不变。

### 4.3 Boss 机制 occurrence

计划内机制继续使用稳定的 `id` 作为 occurrence ID，并新增目录引用：

```ts
export interface CatalogMechanicRef {
  definitionId: string;
  occurrenceId: string;
  catalogVersion: string;
}
```

Boss 机制使用 `TimelineAnchor` 保存时间。可选保留运行时触发信息：

```ts
export interface MechanicRuntimeTrigger {
  event: "cast-start" | "cast-success" | "aura-applied" | "aura-removed";
  abilityGameId: number;
  occurrence: number;
}
```

运行时触发只用于能表达事件相对时间的导出器；没有可靠触发信息时不得猜测。

### 4.4 战术指令

```ts
export type DirectiveScope =
  | { kind: "timed"; anchor: TimelineAnchor }
  | { kind: "phase"; phaseId: string }
  | { kind: "plan" };

export interface TacticalTask {
  id: string;
  kind: "task";
  text: string;
  scope: Exclude<DirectiveScope, { kind: "plan" }>;
  assignees: TargetSelection;
  durationMs: number | null;
  reminder?: { leadMs: number };
}

export interface TacticalNote {
  id: string;
  kind: "note";
  text: string;
  scope: DirectiveScope;
  durationMs: number | null;
}
```

校验规则：

- `task` 可以使用 timed 或 phase scope，文字不能为空，执行者解析后至少包含一个成员。
- `note` 可以使用 timed、phase 或 plan scope，不保存执行者。
- 只有 timed task 可以启用提醒；阶段任务在不支持事件触发的导出器中降级为阶段说明并给出警告。
- `leadMs` 不得小于 0；提醒实际出现时间不得早于当前锚点所属阶段或开怪前 0 秒。
- `durationMs` 为 `null` 时由导出器使用目标格式默认值。
- 删除成员或组后，不自动删除任务；无法解析的执行者进入待处理状态。

### 4.5 成员与策略组

```ts
export interface RosterSlot {
  id: string;
  name: string;
  classSlug: string | null;
  specSlug: string | null;
  role: RaidRole | null;
  color: string;
  groupIds: string[];
  subgroup: 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 | null;
}
```

- `groupIds` 可为空且去重。
- 删除策略组时只移除成员引用，不删除相关任务；使用该组的任务标记为待处理。
- 替换成员时保留原成员 `id` 和 `groupIds`，只更新姓名、职业、专精、职责和颜色。
- 同职业同专精的原技能安排继续有效。
- 同职业不同专精只保留兼容技能；不兼容技能显示待处理警告。
- 不同职业不自动映射技能；原安排保留位置和 slot 引用，但必须标记为职业不兼容。

### 4.6 计划与目录版本

- vNext `RaidPlanDocument.schemaVersion` 从 1 开始，不继承现有 v5 的版本序号或字段兼容责任。
- vNext 不包含 `timelineNotes`、`atMs + mechanicId + offsetMs` 三份时间状态或 Boss 机制直接 `atMs`；只保存本文定义的 directives 与统一 anchor。
- vNext `CatalogManifest.schemaVersion` 从 1 开始。
- `TimelinePreset` 使用新的阶段、机制 occurrence、时间锚点和预设战术说明。
- 每份计划在 `sources` 中保存目录或战斗快照来源；可选 `templateSourceId` 指向创建计划所用的目录来源记录。计划不依赖来源继续存在。
- 旧 v1～v5 计划、旧 v1～v3 目录和现有未投产分享数据不是 vNext 兼容输入；开发 fixture 必须直接使用新格式。

### 4.7 外部身份与来源追溯

WCL 和 Blizzard ID 只能作为外部身份，不能替代 Raidline 内部稳定 ID：

```ts
export interface EncounterExternalIds {
  wclEncounterId?: number;
  wclZoneId?: number;
  blizzardJournalId?: number;
}

export interface PlanSourceRecord {
  id: string;
  kind: "catalog" | "combat-log";
  provider?: "wcl";
  snapshotId?: string;
  reportCode?: string;
  fightId?: number;
  importedAt: number;
  normalizedDataHash?: string;
}

export interface ObjectOrigin {
  sourceId: string;
  sourceEventKeys?: string[];
  conversionRuleIds?: string[];
}
```

规则：

- encounter 使用 Raidline 稳定 ID，并可选保存 WCL encounter ID、zone ID 与 Blizzard journal ID。
- 玩家技能与 Boss 技能的数字法术 ID 对齐 WCL ability game ID；本地化名称与图标只是计划或目录快照，不作为身份。
- 同一 spell ID 可以对应多个语义机制；机制 definition ID 必须独立存在。
- `PlanSourceRecord` 和 `ObjectOrigin` 只用于解释来源。对象必须保存完整内容，来源不存在时仍能正常工作。
- WCL actor ID 和 fight ID 都是来源内局部 ID；任何引用必须同时受 snapshot 或 report code 作用域约束。

- Boss 事件可以分别标记为主时间轴、派生事件、配对/标签证据、结果验证、未来复盘候选或忽略；这些用途不要求互斥。当前转换器只为明确的时间轴用途生成对象。

- 数据库只保存需要查询和恢复的索引、状态、哈希与文件位置；不可变正文通过统一对象存储接口读写。
- 每次 schema 或规范化器升级都必须提供旧 fixture 读取测试，禁止依靠生产数据“自然淘汰”。

## 五、重写边界与旧代码处置

当前项目尚未投产，不承担旧计划、旧目录、旧分享链接或旧服务器数据迁移责任。vNext 采用干净重写，而不是在现有 v5 上继续叠加兼容层。

### 5.1 数据边界

- 计划、目录、战斗快照和转换规则均从各自 schema v1 开始。
- 结构入口只做当前格式的严格解析与校验，不提供 `normalize(any)` 式旧版本猜测、补字段或静默降级。
- 无效当前格式返回可定位的结构错误；语义上暂时无法解析的当前格式对象可以进入待处理状态，但不得和旧格式兼容混为一谈。
- 现有 IndexedDB 测试数据、旧分享对象和旧目录 release 可以清空，不编写迁移器或批量转换脚本。
- 需要保留的牧师样板、Boss 示例和导出样例以人工审阅后的新 schema fixture 重新录入，不通过旧格式运行时迁移。

### 5.2 代码处置

- Git 历史就是旧实现备份，不在新源码中保留 `legacy/`、`v5/`、双路由或长期 feature flag。
- 先在独立分支建立新的领域核心和最小纵向闭环；闭环通过后直接替换旧入口并删除不再使用的旧实现。
- 只复用经测试证明正确、边界清晰的纯函数或行为 fixture，不因为“已经写过”而保留耦合组件。
- 现有首页、双栏编辑器、时间轴视觉、主题、缩放、拖动、选中对象查看详情和分享页交互视为产品基线，未经用户确认不得在架构重写中顺带重新设计。
- 现有大组件的内部状态组织、混合 `core` 文件、托管平台直连存储和宽松 normalize 流程默认视为重写对象；可以拆分组件和改变 props，但应尽量复用已符合需求的可见结构、样式 token 与交互反馈。
- 开始拆分前先为关键桌面尺寸和核心点击/拖动流程建立截图与浏览器回归基线；重构完成后允许细节修复，但不能出现功能入口消失或交互退化。
- 删除旧代码与切换新入口必须发生在同一里程碑内，禁止新旧两套实现长期并存。

### 5.3 鲁棒性门槛

- 重写不等于一次性大爆炸提交。每个里程碑必须形成可运行、可测试、可回退到前一 Git 提交的纵向切片。
- 新抽象必须至少有两个真实调用者，或明确隔离外部系统边界；禁止为了“以后可能用到”建立通用框架。
- 领域层不得导入 React、Next、IndexedDB、SQLite、文件系统、WCL SDK 或托管平台类型。
- WCL、存储和插件格式的失败通过显式结果返回，不得污染或部分写入计划。
- 首个新闭环只覆盖一个真实 Boss fixture、少量成员与牧师关键技能；稳定后再扩大内容范围。

## 六、实现里程碑与顺序

实现者必须按以下顺序执行。每个里程碑通过验收后再进入下一项。

### M1：全新 schema v1 与锚点解析基础

必须完成：

- 新类型、严格结构校验、大小限制和人类可读 fixture；不实现任何旧版本迁移。
- encounter、技能、机制、成员和计划对象的外部 ID 与可选来源追溯结构；来源不得成为对象可用性的前提。
- 阶段、机制、技能安排和指令的统一锚点解析器。
- 全局排序、时间轴范围、拖动预览和冲突检查改为读取解析时间。
- 解析错误类型和待处理提示。
- 为本地保存、撤销重做、快照、发布和只读页定义新的应用接口，不要求复用旧组件。

验收门槛：一个全新 plan v1 fixture 可以严格读取、解析全部锚点、完成往返序列化并拒绝旧 v5 或字段不完整的输入。

### M2：战术任务与阶段视图

必须完成：

- 将编辑入口固定为“技能安排、战术任务、阶段说明”。
- 时间轴增加团队战术轨道。
- 添加、编辑、拖动、删除任务和说明。
- 新增“全程、各阶段”聚焦标签。
- 阶段视图主刻度显示阶段内时间，辅助信息显示预计全局时间。
- 阶段视图保留前一阶段最后 30 秒的淡化上下文，但禁止在聚焦视图中直接拖出当前阶段。
- 全程视图中跨越阶段边界不会自动更换锚点；需要用户在属性面板显式更换阶段或解除关联。

验收门槛：团长可以在不创建虚假技能的情况下表达“P2 开始 18 秒，免疫组去右侧撞球”。

### M3：跨阶段技能检查与 MRT 闭环

必须完成：

- 所有技能按解析后的全局时间继续执行 CD、充能、GCD 和施法检查。
- 阶段视图显示每个成员相关技能进入该阶段时的可用状态。
- 对阶段相对技能给出“该阶段最早可进入时间”，而不只显示红色冲突。
- 实现 MRT 阅读版和 MRT/Kaze 计时版导出。
- 导出窗口显示格式、预览、警告、遗漏项和复制按钮。

验收门槛：选定真实 Boss 后，完整计划可以不手改语法地导入当前使用的 MRT/Kaze 计时方案。

### M4：名单、策略组与替换成员

必须完成：

- 成员多策略组编辑。
- Unicode 纯文本名单粘贴，支持每行只有名字，或名字加职业、专精。
- 未识别职业专精保留为待补充，不拒绝整批导入。
- 替换成员保持 roster slot ID，并按兼容规则更新技能警告。
- 任务中的策略组语义在换人后保持，导出时自动使用新名单。

名单首版不做 OCR，也不开发 WoW 插件。只有纯文本流程经过真实使用仍明显不够时，才单独提出插件导入需求。

验收门槛：替换一名不同职业成员后，策略组和战术任务仍然正确，技能错误被标记且没有错误自动映射。

### M5：下一轮复制与整体平移

必须完成：

- 多选技能安排与战术任务。
- 复制到下一次同目录机制 occurrence。
- 复制到指定阶段并保持阶段内偏移。
- 固定时间整体平移作为高级选项。
- 复制后立即运行目标兼容、CD、充能和施法检查。
- 不自动替用户选择新的技能执行人。

验收门槛：一轮机制的技能与任务可以通过一次操作复制到下一轮，并保留相对关系。

### M6：可持续目录升级

必须完成：

- 全新 catalog schema v1、严格校验和人类可读 fixture；不实现旧目录迁移。
- 预设机制 occurrence 使用持久化稳定 ID，禁止应用时随机生成。
- 目录 release 不可变；同名版本重复发布必须失败。
- 用户只看到 current release，但旧 release 继续保留在服务器持久数据目录中供差异比较。
- 技能、阶段、机制 occurrence 和预设说明的差异预览。
- 同一预设升级使用 base release、当前计划、new release 三方比较。

三方合并规则：

- 计划内容等于 base、new 发生变化：可安全更新。
- 计划内容已偏离 base、new 未变化：保留用户内容。
- 计划和 new 都偏离 base：显示冲突并由用户选择。
- new 新增 occurrence：列为可加入，不自动插入。
- new 删除 occurrence：标记目录已移除，不自动删除计划对象。
- 阶段结构或 ordinal 改变：必须显示映射预览并由用户确认。
- 旧 base release 不可用时，只提供保守的两方预览，禁止自动覆盖。

预设行为：

- 新建或空计划可以直接应用预设。
- 已有内容的计划不能通过“应用预设”切换为另一 Boss 并清空安排；应创建新计划。
- 同 Boss、同 presetId 的更新必须进入目录升级流程。

验收门槛：发布一个包含技能 CD、P2 时间和机制时间变化的新目录后，既有安排不被清空，用户可预览并分别决定更新项。

### M7：NSRT 与 STT 导出

统一公共接口：

```ts
export type ExportTarget =

  | "mrt-kaze"
  | "nsrt"
  | "stt";

  itemId?: string;

  warnings: ExportWarning[];
  omittedItemIds: string[];

```

导出要求：

- MRT/Kaze：pull anchor 输出 `{time:MM:SS}`；phase anchor 输出 `{time:MM:SS,pN}`；有可靠运行时触发的 mechanic anchor 可以输出事件相对格式。
- NSRT：输出 `time + ph + tag + text/spellid + dur`；自定义策略组展开为当前具体玩家名并产生 `group-expanded` 提示。
- STT：输出开怪时间、`pN` 阶段时间、可用的技能事件和人员别名；策略组优先生成别名映射。
- mechanic anchor 若无法生成可靠事件触发，应先尝试转换为其所属 phase 的相对时间；仍不能表达时才降级为预计开怪时间，并必须产生警告。
- phase 或 plan scope 的说明进入阅读文字，不强制生成战斗提醒。
- 任何目标为空、职业不兼容或时间未解析的任务不得生成看似正常的提醒文本。

验收门槛：三种计时格式均有固定 golden fixture，并各有一份经过实际插件导入验证的样例。

### M8：基础闭环回归与文档同步

必须完成：

- 完整自动化测试、生产构建与真实浏览器验收。
- 用真实史诗 Boss 数据走通建轴、调阶段、换人、复制、升级目录、导出和发布。
- README 更新 schema、目录发布、服务器存储和导出目标说明。
- 需求索引、验收结果和变更记录更新。
- 本地浏览器回归只验证点击流程、布局和交互；该里程碑不代表大陆生产后端或长期存储已经验收。

验收门槛：在完全关闭 WCL 能力的情况下，预设/空白建轴、编辑、保存、分享和至少一种实际采用的插件导出形成稳定闭环。

### M9：可移植后端与服务器持久化基础

必须完成：

- 将对象存储、结构化元数据、导入任务和时间来源封装为独立接口，业务代码不读取具体文件系统、托管平台或数据库运行时绑定。
- 实现服务器本地 SQLite（WAL）元数据存储与内容寻址文件对象存储。
- 数据库迁移采用顺序版本，启动时只执行已提交、可重复检查的迁移，不临时拼接 schema。
- 对象写入遵循“临时文件 → 校验大小与哈希 → 原子改名 → 数据库提交引用”的顺序。
- 提供数据库与对象目录的一致备份脚本、恢复说明和至少一次自动化恢复测试。
- 本地文件适配器与未来服务器适配器通过同一 `ObjectStore` 契约测试，确保只是存储位置不同而不是业务行为不同。

验收门槛：在普通 Linux 单机、无托管平台运行时绑定的环境中，可保存和读取目录 release、发布计划、导入任务元数据及测试快照；重启后数据完整。

### M10：WCL 服务端读取与规范化快照

必须完成：

- 解析 `cn.warcraftlogs.com` 与其他 WCL 官方报告链接，严格提取 report code 与 fight 参数，拒绝非允许域名和异常 URL。
- 实现 WCL v2 client credentials 服务端认证、token 缓存、GraphQL 查询、事件分页、额度感知、超时、有限重试和取消。
- API base URL 通过配置注入；大陆部署前用真实认证请求验证选定入口，失败时给出可诊断但不泄露密钥的错误。
- 分阶段读取 report、fight、master data、phase transitions 和采集规则要求的事件。
- 将 report-relative 时间统一转换为 pull-relative 时间，并正确限定 fight ID、actor ID 和 phase ID 的作用域。
- 按 `reportCode + fightId + reportRevision + normalizerVersion + contentHash` 幂等保存不可变快照。
- 不保存 access token、client secret、完整原始 GraphQL 响应或与排轴无关的事件集合。

验收门槛：对一条真实公开 WCL 战斗链接连续导入两次只产生一个相同快照；WCL revision 或规范化器变化后产生新快照，旧快照保持可读。

### M11：人工规则、导入预览与创建计划

必须完成：

- `/admin` 增加 encounter Boss 采集/转换规则与全局玩家技能提取 profile 的分区管理，支持表单编辑、复制、启停、结构校验、冲突检查和时间轴预览。
- 规则 draft 可修改，published release 不可变；发布必须记录 revision、样例报告和验证时间。
- 首页增加粘贴 WCL 链接入口、fight 选择、异步进度、失败重试和导入草稿预览。
- 预览分别展示人员、阶段、Boss 机制、玩家关键技能、未知事件、重复项、歧义和推断关联。
- 用户逐类或逐项确认后创建新计划；生成的每个对象复制完整快照并附带可选来源。
- 导入生成稳定 roster slot；替换成自己团队成员后，技能安排、任务和策略组保持。
- 在已有计划中粘贴 WCL 时不进入导入覆盖流程，默认进入 M12 对比。

验收门槛：使用一份真实报告、精确匹配的已发布 encounter profile 和适用的全局玩家技能提取 profile，能够只选择部分人员、机制和玩家关键技能创建独立计划；随后删除本地导入快照，计划仍能打开、编辑和导出。

### M12：开荒战斗对比

必须完成：

- 将选定计划 revision 与新 WCL 快照配对，生成匹配、提前、延后、遗漏、额外、错误成员、错误目标、歧义和不可验证结果。
- 对比视图可按阶段、机制、成员和技能筛选，并能定位到时间轴对象与对应观察事件。
- 显示使用的计划 hash、快照 ID、转换 profile revision 与允许误差，确保结果可追溯。
- 对比结果默认保存在本地或服务器分析记录中，不写回计划和普通分享。
- “采用实际时间/成员”必须逐项操作、展示变化并先建立检查点。
- 不生成战术执行总分，不把单次战斗自动升级为目录预设。

验收门槛：同一计划对比一份真实开荒日志后可以定位至少一项时间偏差和一项遗漏；关闭对比不改变计划 hash。

### M13：中国大陆生产部署

必须完成：

- 提供普通 Linux 服务器的版本化部署说明和可重复启动方式，应用、SQLite 数据库与对象目录均使用明确的持久化绝对路径。
- 反向代理、HTTPS、域名、请求体限制、WCL 密钥、管理员口令和备份密钥通过生产配置注入，不写入仓库或前端。
- 应用进程只监听内网或本机端口；数据库与数据目录不直接暴露公网。
- 在目标大陆服务器实测首页、编辑器、分享、导出、`cn.warcraftlogs.com` 报告链接解析及选定 WCL API endpoint 的认证请求。
- WCL 外部请求失败时，手动建轴、服务器数据读取和导出不受影响；导入任务可在恢复后人工重试。
- 完成每日数据库与对象目录备份、保留策略、哈希检查、异机副本和恢复演练；未验证恢复的备份不计入验收。
- 正式对互联网提供服务前，根据网站性质与接入商当前要求完成 ICP 备案或许可；联网后按适用规定完成公安备案，并在页面按要求展示备案信息。
- 当前仓库不维护第三方托管预览或部署配置；本地交互回归不作为生产可用性证据。

验收门槛：从全新服务器和一份备份恢复后，能够打开已发布计划、读取目录、查看已有 WCL 快照并完成一次新导入与插件导出，全流程不调用托管平台专有接口。

## 七、界面与交互要求

### 7.1 时间轴轨道

建议固定顺序：

1. 阶段与阶段说明。
2. Boss 机制。
3. 团队战术任务。
4. 成员技能安排。

战术任务卡片显示任务文本和执行者摘要，不显示不存在的技能图标。

BOSS 机制轨道同时提供两种布局：

- 机制定义必须用严格、供应商无关的 `timelinePresentation.parts` 明确列出区间、判定点、阶段说明和视觉语义；一个 occurrence 可以表达多个阶段，视图不得根据技能名或法术 ID 推断。
- 紧凑：每个自动避让子轨道分为阶段说明与条形图两层，按当前横/纵方向和缩放下的所有文字、区间和判定点碰撞，确定性地分配最少子轨道。阶段气泡左沿固定在所属区间起点或判定时点，不再使用连接虚线；同层碰撞时占用下一说明层并只增高受影响轨道，两层仍冲突时在不遮盖其他内容的前提下缩短气泡并显示省略号，同一时点无法通过省略分开时继续增加说明层。
- 宽松：按稳定 `definitionId` 固定机制类型子轨道，同一机制定义始终位于同一行或列；左侧只显示机制类型名，时间区域只显示条形和判定点，不得按本地化名称归类。
- 区间视觉统一分为背景/无效果、读条/预警、效果持续；时点分为普通点与高亮机制判定。横向和纵向使用同一语义，仅转置布局。
- 紧凑模式的每个阶段说明始终显示为薄边框、淡色填充的独立气泡，选中只增强色彩，不控制气泡是否出现；每个气泡或条形的悬停提示只包含自身阶段名称与时间，完整机制说明只在对象检查器显示。
- 单击任意阶段气泡、区间或判定点必须选择整个 occurrence；拖动仍移动整个 occurrence。时间轴缩放范围固定为 `4×–16×`，包括从旧本机偏好加载时也必须夹取到该范围。
- 布局模式、计算后的子轨道索引和轨道高度都是本机派生视图，不写入计划、目录、WCL 快照或分享正文。

### 7.2 阶段聚焦

- 标签顺序按 `ordinal`。
- 标签名称使用用户阶段名，不直接用数组下标。
- 选中阶段后，横轴 0 表示该阶段开始。
- 对象提示同时显示“P2 + 00:18”和“预计全程 03:42”。
- 阶段边界变化后，视图、冲突和导出预览立即重新计算。
- 导出阶段相对文本不得因为预计阶段时间变化而改变。

### 7.3 待处理状态

以下情况必须在时间轴和检查面板同时可见：

- 锚点引用的阶段或机制不存在。
- 战术任务没有实际执行者。
- 替换成员后技能不兼容。
- 目录 occurrence 已删除或发生冲突。
- 导出目标不能表达当前提醒。

待处理问题不能阻止用户打开或保存计划，但必须阻止生成错误的对应提醒行。

### 7.4 WCL 链接导入

- 首页提供单一的“粘贴 WCL 战斗链接”入口，不要求用户理解 report code、fight ID 或 GraphQL。
- 接受 `cn.warcraftlogs.com` 等允许列表中的 WCL 官方链接；没有明确 fight 时先显示该报告可选 Boss 战斗。
- 导入采用异步状态：等待、读取报告、读取战斗、规范化、转换、等待确认、完成、可重试失败。
- 失败信息应区分无效链接、非公开报告、战斗不存在、WCL 认证失败、WCL 网络失败、额度不足、规则缺失、规则歧义和本地/服务器存储失败。
- 进度页面关闭或刷新后可以继续查看同一任务，不会重复创建快照。
- 导入预览必须允许整类开关与逐项选择，默认不选中歧义、未知和低置信度推断项。
- 创建计划后显示“来源于一次 WCL 观察快照”，但不显示为“已同步”；计划允许清除来源说明而不改变内容。

### 7.5 人工转换管理

- 管理后台按游戏版本、团本、encounter 展示 Boss conversion profile，并在独立区域按游戏版本展示全局 PlayerSkillExtractionProfile。
- 规则表单显示事件类型、ability ID、来源 NPC、目标对象、去重窗口、转换目标、说明和验证样例。
- 提供样例快照事件浏览器；管理员可以从观察事件创建规则草稿，但必须人工选择转换目标 definition。
- 时间轴预览同时显示原始观察事件、转换后对象和未匹配事件，颜色与图例明确区分。
- 发布前展示本 revision 相对上一 revision 的采集范围、转换行为和 fixture 差异。
- 已发布规则只能停用或复制为新 revision，禁止就地编辑历史 release。

### 7.6 开荒对比视图

- 在现有计划中粘贴 WCL 链接默认打开对比向导，先选择计划 revision 和战斗，再建立成员映射。
- 对比层叠加在现有时间轴上，不建立第二套编辑时间轴；计划对象与实际事件必须有不同视觉语义。
- 点击结果时同时显示计划时间、实际时间、偏移、匹配依据、使用规则和无法确定的原因。
- 点击空白或关闭对比不会修改计划；只有显式“应用此项”才进入正常编辑历史。
- 本地原型使用固定匿名 fixture 验证完整交互；真实 WCL、数据库和恢复流程只在生产同构环境验收。

## 八、冲突检查规则

- 所有检查先将可解析对象投影到预计全局时间，再按成员和技能排序。
- 继续支持现有单充能、多充能、GCD、施法区间和职业专精检查。
- 阶段相对对象的检查结果必须随 `estimatedStartMs` 实时变化。
- 对跨阶段 CD 冲突，除普通错误外还应计算阶段开始阈值：

```text
阶段最早开始时间 = 上次使用时间 + 技能恢复需求 - 本阶段内使用偏移
```

- 如果技能数据状态不是 verified，应在结果中说明检查基于当前计划快照，不能声称为正式服绝对结论。
- 导出前必须再次运行检查，但允许用户复制带有非致命警告的文本；未解析目标或时间属于阻断该条目的错误。

## 九、可持续维护要求

### 9.1 内容范围

只维护：

- 当前史诗团本主要机制、阶段和排轴相关时间。
- 团队减伤、外部减伤、个人保命、免疫、关键位移和明确需要安排的技能。
- 会改变 CD、充能或目标数量的关键天赋变体。

不维护：

- 正式服全部技能。
- 所有难度、所有历史团本。
- 完整伤害公式和治疗模拟。
- 与排轴无关的天赋和技能说明。

### 9.2 内容状态

每个目录条目继续保存：

- 游戏版本和可选客户端 build。
- 数据状态：未配置、待正式服核实、已核实、旧数据、自定义。
- 来源、核实时间和必要说明。
- 稳定 definition ID。
- 预设内稳定 occurrence ID。

### 9.3 更新流程

每次补丁只处理变更项：

1. 创建新的不可变目录版本。
2. 更新发生变化的技能、阶段和机制 occurrence。
3. 运行结构校验和对应导出 fixture。
4. 用至少一份基于上一目录 release 创建的 vNext 计划执行升级预览。
5. 所有 release 对象写入成功后，最后更新 `catalog/current.json`。

只要坚持当前团本与排轴相关数据范围，该维护模式可以由小团队长期承担。若扩展为全游戏数据库、全难度攻略或自动复盘平台，则不再属于可持续范围。

### 9.4 Boss 技能收录流程

每个新 Boss 按以下顺序制作时间轴规则：

1. 读取 fight 元数据并确认 encounterID、游戏版本和史诗难度，禁止从技能名反推 encounter。
2. 在被 Git 忽略的本地样本中聚合事件族，比较多场 occurrence 的时间稳定性。
3. 分别确认机制的预警开始、判定点、效果结束、同波聚类、跨 ID 关联和派生阶段；同一轮的连续处理阶段优先进入一个定义和一个 occurrence，而不是生成重复机制对象。
4. 独立记录时间轴用途与未来复盘价值；复盘后置不等于删除验证或失败证据。
5. 只有稳定、语义明确且要求玩家处理的事件进入预期时间轴 fixture；随机、失败或动态事件保持待审。
6. 用匿名小型 fixture 预览完整转换结果，人工核准后才发布 EncounterConversionProfile。
7. 玩家技能由全局 PlayerSkillExtractionProfile 统一维护，不在 Boss 收录流程中复制或临时增删。

## 十、自动化测试与验收场景

### 10.1 schema 与严格校验

- [ ] plan v1、catalog v1、combat log snapshot v1 和 conversion profile v1 均有可读 fixture、结构校验和大小/数量限制。
- [ ] 当前格式完成解析与序列化往返后语义和内容哈希稳定。
- [ ] 旧 plan v5、旧 catalog v3、未知 schemaVersion 和缺少必需字段的输入被明确拒绝，不被猜测性补全。
- [ ] 当前格式中的孤立阶段、机制、成员或组引用产生待处理问题，不会被静默删除。
- [ ] 牧师样板和首个 Boss 数据通过人工审阅的新 fixture 载入，不依赖迁移器。
- [ ] 公共 schema 不包含 React、Next、IndexedDB、SQLite、WCL GraphQL 或插件序列化专属类型。

### 10.2 阶段与锚点

- [ ] 移动 P2 时，phase anchor 对象整体移动，pull anchor 对象不动。
- [ ] 移动 Boss 机制时，mechanic anchor 对象跟随，偏移不变。
- [ ] 阶段视图和全程视图显示的是同一对象集合。
- [ ] BOSS 紧凑轨道不会让标签/时间区间碰撞，且使用确定性的最少子轨道；宽松轨道按 `definitionId` 稳定归类。
- [ ] 切换轨道模式不会改变计划 hash、机制锚点或 WCL 转换结果。
- [ ] 阶段预计时间改变不会改变阶段相对导出文本。
- [ ] 重复显示名称的阶段仍按稳定 ID 和 ordinal 正确导出。

### 10.3 技能检查

- [ ] 同阶段与跨阶段单充能检查正确。
- [ ] 多充能串行恢复正确。
- [ ] GCD、施法和引导区间重叠检查正确。
- [ ] 显示跨阶段最早进入阈值。
- [ ] 替换职业后不兼容技能被标记且不被自动替换。

### 10.4 战术任务与名单

- [ ] 战术任务支持全团、策略组、职责和具体成员。
- [ ] 阶段说明不要求精确时间和执行者。
- [ ] Unicode 名单粘贴不会损坏繁体、日本汉字或特殊字符。
- [ ] 同 ID 替换成员后，组与任务引用继续有效。
- [ ] 删除策略组后相关任务进入待处理状态。
- [ ] 复制下一轮后锚点、目标和偏移正确，并立即产生冲突结果。

### 10.5 目录升级

- [ ] 技能 CD 更新不移动安排，只重新检查。

- [ ] 用户改过的内容不会被 new release 静默覆盖。
- [ ] 新 occurrence 不自动插入，删除 occurrence 不自动删除。
- [ ] 阶段结构变化需要显式确认。
- [ ] 升级和重新应用预设都不会清空 roster、assignments、directives 或成员技能变体。

## 十一、最终用户验收流程

使用一个真实当前史诗 Boss、一份真实 20 人名单、两份该 Boss 的公开 WCL 战斗和一个大陆生产同构服务器环境：

1. 在 WCL 功能关闭时，从目录预设创建计划。
2. 建立免疫组、打断组和左右分组。
3. 添加技能安排、定时战术任务和阶段说明。
4. 将 P2 预计开始时间提前，确认全局位置和跨阶段 CD 结论更新。
5. 将第一轮任务复制到下一次同名机制。
6. 用不同职业成员替换一名团员，确认组任务保留、技能冲突出现。
7. 分别生成 MRT 阅读版、MRT/Kaze、NSRT 和 STT 输出。
8. 至少将实际采用的插件格式导入游戏，不做任何手工语法修正。
9. 发布计划并从只读链接复制回另一份本地计划。
10. 发布一个目录更新，确认基于上一目录 release 的 vNext 计划保持原样，并能预览安全更新与冲突项。
11. 在管理员界面为该 encounter 查看并发布人工采集/转换 profile。
12. 粘贴第一份公开 WCL 链接，预览人员、阶段、机制、关键技能、未知事件和歧义，只选择部分内容创建新计划。
13. 将导入计划中的原玩家替换为本团成员，确认 slot、安排、任务和分组保持，并在断开 WCL 来源后成功导出。
14. 在原手工计划中粘贴第二份 WCL 链接，完成成员映射并查看至少一项时间偏差和一项遗漏，不改变计划 hash。
15. 将数据库与对象目录恢复到全新大陆服务器环境，确认已发布计划、目录、规则、快照和导入记录可用，并再次完成 WCL 导入与插件导出。
16. 暂时阻断 WCL 外部请求，确认手动建轴、编辑、分享和导出仍然可用。

只有以上流程完整通过，需求才可标记为已完成。

## 十二、本次明确不做

- 旧 plan v1～v5、旧 catalog v1～v3、旧分享对象和旧 IndexedDB 数据迁移或兼容读取。
- 2D 站位动画和路线演示。
- OCR 名单识别。
- WCL 私有报告 OAuth、账号绑定、持续同步和自动轮询。
- 完整镜像 WCL 原始报告、保存所有伤害/治疗事件或建设通用日志分析器。
- 自动复盘结论、战术执行总分、自动生成正式预设或自动推断团长提醒文字。
- 实时多人协作。
- 账号、公会云成员库和云端自动保存。
- 公共打法市场或开放模式。
- AI 自动生成打法或自动选择技能执行人。
- 完整成员网页门户。
- 精确动态击杀时间模拟。
- MRT 原生 Reminders 配置生成。
- 正式服全部技能、全部难度和历史团本数据库。
- 多实例、自动故障转移和跨地域高可用；只有单机架构出现明确容量或可用性需求后才单独立项。
- 将任何单一托管平台作为生产运行前提。
- 无明确新需求的整站视觉重做；本轮目标是保留现有前端体验并替换内部结构。

普通成员主要通过游戏内 MRT、STT 或 NSRT 消费结果。成员筛选和个人导出只有在团长检查流程需要时才作为辅助功能实现。

## 十三、AI 执行约束

- 实现前先阅读本文、需求索引、README 和当前相关类型、时间轴、冲突、目录、导出及旧 normalize 代码；旧代码只作为行为参考，不作为兼容目标。
- 不得一次性跨越多个里程碑提交未经验证的大改。
- 每个里程碑先更新或新增测试，再完成实现和回归。
- 保留用户已有改动，不重置或覆盖无关文件。
- 不保留仅为旧 schema、旧路由或旧组件服务的兼容代码；Git 历史作为唯一旧实现归档。
- 不得把任何托管平台、数据库或文件系统类型扩散到领域模型和业务服务。
- 生产默认使用服务器本地 SQLite 与持久数据目录；只有经过容量、并发或高可用证据并获得用户确认后才引入 PostgreSQL 或外部对象存储。
- 本地原型仅用于临时交互验证；不得读取正式 WCL 密钥、正式数据库或唯一备份，也不得把本地构建成功当作生产完成。
- WCL client、规范化器、转换器、计划模型和导出器必须保持单向依赖，禁止在计划编辑路径中实时查询 WCL。
- 不把 access token、client secret、WCL 原始 GraphQL payload 或数据库连接信息写入计划、浏览器存储、日志 fixture 或仓库。
- encounter 事件采集和转换必须读取人工发布的规则，禁止在导入代码中散落无法审查的 ability ID 与隐式判断。
- 玩家关键技能必须读取独立发布的全局 PlayerSkillExtractionProfile；不得复制到 encounter profile，也不得用玩家规则猜测 Boss 机制。
- 不把插件格式字段写进计划 schema。
- 不通过自动删除、清空安排或静默降级来“修复”异常数据。
- 如果外部插件格式与本文示例发生变化，以对应插件当前官方文档或源码为准，同时更新导出 fixture 和本文变更记录。
- 遇到会改变固定产品决策的情况时停止实现，记录具体冲突并请求用户决策。
