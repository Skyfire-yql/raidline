# Raidline WCL 第一阶段：公开报告与阶段探针

## 目标

建立最小、真实、可替换的 WCL 网络边界：先读取公开报告、Boss 战斗和 WCL 官方阶段；用户选择史诗 fight 后，再精确加载 encounter profile、分页读取所需事件并生成匿名导入预览。所选机制只能由用户显式保存到浏览器本地计划，不保存服务器战斗快照；开发者本地研究工具仍可在隔离目录完整缓存指定样本事件。

当前真实网站回归样本使用：

- 报告：`https://cn.warcraftlogs.com/reports/LgdFn8NyAGRqWT3V?fight=64`
- Boss：万毒邪祟者瓦什尼克，正式服 encounter `3455`
- 战斗：fight 64，史诗击杀
- 选择原因：用户提供的正式服报告，可同时验证链接解析、精确 profile、事件分页、中文显示和本地计划导入。

## 固定决策

- 接受 `cn.warcraftlogs.com` 和明确允许的 WCL 零售官方区域域名；只接受 HTTPS `/reports/{reportCode}` 链接，以及空、正整数或 `last` 的 fight 参数。
- 浏览器只调用 Raidline 自己的 `/api/wcl/reports/probe` 与 `/api/wcl/reports/import-preview`。WCL client secret、Basic 凭据和 access token 只存在于服务端运行时。
- 服务端通过 OAuth client credentials 调用可配置的 WCL token 与 GraphQL endpoint；token 只在进程内缓存，不写浏览器、计划、对象存储或仓库。
- 读取 `ReportFight.phaseTransitions`，将报告相对时间换算为开怪后毫秒时间。重复语义阶段使用 `occurrenceIndex` 区分；WCL 未提供 0 秒阶段时只为探针显示补 P1=0。
- WCL 阶段划分作为后续提醒轴的主要基线。插件模型优先使用“监听少量阶段标记 → 重置阶段计时器 → 阶段内相对时间提醒”，不为每个 Boss 技能建立运行时单位事件监听。
- 探针可以展示非史诗战斗，但只把史诗标为可用于后续转换；非史诗数据不得创建快照、草稿或计划。
- 探针与导入预览都不做服务器写入。网络失败只能使当前 WCL 请求失败，不能影响手工建轴、打开既有本地计划、发布或导出。

## 本阶段实现

- 严格 WCL 链接解析。
- 服务端 OAuth client credentials、并发 token 复用、15 秒超时和一次有限重试。
- GraphQL 报告、战斗与 `phaseTransitions` 查询及严格 DTO 校验。
- 首页报告链接输入、战斗选择和阶段时间预览。
- 史诗难度边界、精确 encounter/profile 选择、事件分页、匿名清洗、机制候选勾选和浏览器本地计划保存。
- 单元 fixture 与 API/HTML 回归；fixture 中不包含真实 token、client secret 或完整原始报告。

## 明确不做

- 不把 GraphQL 原始响应、玩家姓名、敏感请求头、规范化快照或导入草稿返回浏览器或持久化。
- 不把 WCL 阶段或机制静默写入计划；只有用户显式勾选并确认后才创建浏览器本地计划。
- 不确定 Boss 技能白名单；该规则由用户人工维护。
- 当前导入只创建 Boss 机制时间轴，不生成玩家名单、个人技能安排或复盘归因。
- 当前仓库不维护托管平台部署配置，WCL 凭据只允许进入本机或未来自有服务端环境变量。

## 下一阶段输入

用户为 Vashnik 样本人工确定：

1. 哪些敌对施法或光环是阶段标记。
2. 哪些 Boss 技能需要进入机制时间轴。
3. 同一语义阶段重复出现时的规则，以及哪些事件只用于配对、标签、验证或未来复盘、不进入计划。
4. 独立的全局 `PlayerSkillExtractionProfile` 需要提取哪些个人减伤和治疗技能；该清单不属于 Vashnik profile。

采集规则与转换规则必须独立、版本化、可审查。伤害和爆发技能之后可以新增规则类别，不需要修改 `RaidPlanDocument`。

## Boss 时间轴收录原则

- 当前优先目标是把 WCL 战斗记录转换为玩家可用的 Boss 机制时间轴；复盘界面和玩家失误归因后置。
- “是否生成时间轴对象”与“是否具有未来复盘价值”互不排斥。未进入时间轴的失败结果、伤害证据和关系事件仍可保留人工标记，不得因为复盘暂缓而改成无价值或删除。
- 每个时间轴机制分别确认预警开始、机制判定和效果结束；`begincast → cast` 是游戏内反应区间，插件或网页更早的提醒提前量属于预设，不从 WCL 事件时间反推。
- 同一轮技能若包含多个连续处理阶段，使用一个机制定义和一个 occurrence 保存，并以定义内的区间与判定点分别命名；不得为了显示第二个阶段而重复生成独立机制对象。复合阶段仍可通过 `cast-start`、`impact`、`end` 锚点引用。
- 同一次机制造成的多目标光环、AOE 或伤害必须按人工规则聚类，不能为每名玩家生成一条 Boss 机制。
- 只有跨样本时间稳定、语义明确且要求玩家处理的事件才生成时间轴对象。时间不稳定的事件可能来自小怪死亡、随机选择、玩家失误或失败路径，继续保留待审，不猜测转换。
- WCL 快照与导入草稿保留毫秒；复制到当前整秒 plan v1 时向更早方向吸附到整秒，即 `floor(atMs / 1000) * 1000`。

## Vashnik 首版时间轴决定

- 五场没有 WCL `phaseTransitions`，首版按单阶段处理；痛饮（Imbibe）只帮助识别循环和记忆，不建立阶段。
- 痛饮使用 `1284663 begincast → cast` 显示约 4 秒读条区间；`1284669/1284670/1284671` 只用于标注本轮血/火/暗组合。更长持续区间的终点后续再定。
- 恶性催化剂 → 催化胆汁（Malignant Catalyst → Catalytic Bile）作为一个复合机制：`1282516 begincast` 是开始，`1282516 cast` 与聚类后的 `1282525 damage` 是全团伤害判定，聚类后的 `1282602 damage` 是接圈判定。`1282616 damage` 保留为漏接失败证据，不生成正常时间轴 occurrence。
- 瘟疫泡沫 → 瘟疫浪潮（Plague Froth → Plague Wave）使用相同复合机制模型：聚类后的 `1281913 applydebuff` 是开始，对应 `removedebuff` 同时是泡沫结束和浪潮判定；不生成独立浪潮 occurrence，也不依赖 `1295798 damage` 判断海浪是否生成。
- 滴毒之牙（Dripping Fangs）使用 `1280935 begincast → cast/damage` 表达读条和判定；`1280934` 的减益、层数与 Tick 不单独生成机制。
- 虹吸感染（Siphoning Infection）从 `1295224 applydebuff` 开始；同轮多目标合并为一个机制。鲜血虹吸（Siphon Blood）暂不生成独立机制，但保留未来审查标记。
- 毒性蒸汽（Toxic Vapor）只追踪 `1284563` 的初始光环与层数变化；`1284561` Tick 不进入时间轴。
- 恶念（Malignance）独立保留，但首版不进入时间轴；它可能与 Malignant Tumor 死亡或其他动态状态相关，当前证据不足以稳定转换。
- Imbibe 派生机制和其余敌方事件后续逐批审查；稳定且语义明确时再加入时间轴，否则保持待审。

## 本地完整事件研究流程

为 PTR Boss 建立人工转换规则时，可以在被 Git 忽略的 `work/` 目录完整缓存样本战斗。完整缓存只作为开发和测试真值，不进入 `RaidPlanDocument`、分享对象、网站 API 或当前长期快照契约。

- `pnpm wcl:download -- --report <报告链接或 ID> --fights <fight IDs>` 逐页下载完整事件，单页 gzip 压缩并记录哈希；已完成页面不会重复下载，中断后从最后一个完整 `nextPageTimestamp` 继续。
- 当前无自有 WCL 凭据时，下载器只允许使用可替换的兼容测试源；它不是生产依赖。正式接入必须改为 Raidline 自有服务端凭据和 WCL v2 GraphQL。
- `pnpm wcl:review -- --report <报告 ID> --fights <fight IDs>` 逐页读取缓存，按“来源语义 + NPC game ID + ability ID”归并事件族，并按 250ms 合并同一波多目标事件。
- `pnpm wcl:convert -- --input-root <缓存根目录>` 先读取严格 fight 元数据，确认正式 WCL `encounterID` 和史诗难度，再精确选择本地模拟数据库中的 published encounter/player profile；随后逐页读取完整事件，输出 gzip 清洗快照、毫秒导入草稿、整秒计划和汇总。所有产物仍写入被 Git 忽略的报告目录。
- 原始事件全部保留；玩家对敌方伤害、逐次治疗、宠物噪声等仅从第一轮候选中排除，并列入完整排除索引。带有 Boss 血量的事件先提取血量采样再排除。
- 审查结果分别列出敌方/系统/未知事件、玩家技能候选、默认排除项和可编辑人工决定；每个候选保留五场逐波时间、事件类型、来源 actor、资料说明和稳定性摘要。
- `absorbed`、`aurabroken` 等关系事件的字段含义随场景变化，不能把 `extraAbility` 统一解释为攻击技能。它们只作为关系证据，人工确认后才能形成规则。

首批完整基准为报告 `baxm3wf8MDvF6V7W` 的 fight 26、28、29、31、32，共 1,883,421 条原始事件。五场均未返回 WCL `phaseTransitions`；当前 Wowhead PTR 指南将 Vashnik 描述为单阶段循环，因此本样本先按开怪时间比较，阶段规则待人工确认。

历史测试服完整事件样本的 WCL `encounterID` 为 `3134`；用户提供的正式服报告 `LgdFn8NyAGRqWT3V` fight 64 元数据确认 `encounterID = 3455`。两者是同一 Boss 的独立精确 profile 键，禁止全局 fallback。兼容缓存中的 `fight.boss = 53455` 是另一套来源标识，也不得当作 encounterID。历史 fight 32 的 413,842 条事件清洗为 7,896 条并生成 53 个机制对象；当前正式服 fight 64 分页读取 150,497 条、匿名保留 5,730 条并生成 50 个中文机制候选，警告和未解析事件均为 0。

正式服中文显示名在 profile v2 中单独发布，未原地修改 v1。WCL 已出现技能以正式服中文报告 `LgdFn8NyAGRqWT3V` 的同 spell ID 中英文 masterData 对照为主要证据；`1295224` 虹吸感染和 `1295229` 鲜血虹吸由 Wowhead 正式服简中 spell 页面补证。英文原名、spell ID、来源 URL 与版本说明保留在定义 verification 中；`1282078`、`1284669`、`1286872` 未取得直接证据，不猜译名。

## 转换规则的 Encounter 与数据库作用域

- 正式导入必须先从 WCL fight 元数据确认 `encounterID`，完成难度检查后才能读取任何转换规则。
- 已确认规则以数据库中的版本化 `EncounterConversionProfile` 保存，至少由 `encounterID`、游戏版本、profile 版本和发布状态唯一定位；Markdown/JSON 研究文件不是生产规则源。
- Boss 机制、阶段信号、敌方事件选择、事件关联和去重方式属于 encounter profile。
- 个人减伤、治疗等玩家技能由独立、版本化的全局 `PlayerSkillExtractionProfile` 统一提取并引用全局技能定义；不得把玩家技能清单复制到每个 Boss profile，也不得用全局玩家规则猜测 Boss 机制。
- 禁止因为两个 Boss 使用相同法术名、法术 ID 或事件形状，就把一个 encounter 的规则应用到另一个 encounter。
- 没有精确匹配且已发布的 profile 时，导入只报告“该遭遇尚未配置”，不得执行全局 fallback、猜测转换或创建半可信计划。
- profile 更新必须生成新版本；既有战斗快照和已经确认进入计划的定义快照不被后台静默重写。

## 验收

- 能解析给定 `cn` 报告链接，并严格拒绝伪造域名、HTTP、异常 report code 和异常 fight。
- 使用服务端凭据读取报告及全部 Boss 战斗；不在 HTML、API 结果或错误中暴露凭据。
- 带 `fight=64` 的链接可直接选择 fight 64；不带 fight 时可看到每场时长、Boss 血量百分比、难度与结果后再选择。
- OAuth token 在有效期内复用；WCL 超时、认证、额度、报告不存在和结构异常返回可区分错误。
- 探针不创建或修改计划；导入预览也不写服务器数据，只有用户显式确认后才创建浏览器本地计划，且不写分享、目录或 WCL 快照。
- 正式服 fight 64 导入返回中文 profile v2 的 50 个匿名机制候选；API 响应与 Git 状态中不出现原始日志、玩家姓名、敏感头、清洗快照或导入草稿。
